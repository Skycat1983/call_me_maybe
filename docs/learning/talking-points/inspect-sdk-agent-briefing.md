# Agent Briefing: `inspect_sdk.py`

Use this document to prepare an agent for a voice discussion about
`experiments/inspect_sdk.py`. It is deliberately more detailed than a normal
waypoint talking-points file so the agent can answer follow-up questions
without first reconstructing the experiment from the repository.

## Essential summary

`inspect_sdk.py` is a small diagnostic program written locally with help from
the AI assistant. It was not supplied with the project, downloaded, generated
by `uv`, or generated by the Qwen model.

It was designed by reading the supplied SDK's public interface and turning
the project's open questions into observable checks. The program:

1. constructs `Small_LLM_Model`;
2. encodes one prompt into token IDs;
3. tests two forms of decoding;
4. asks the SDK for its three tokenizer-file paths;
5. requests one vector of next-token logits;
6. finds and decodes the ten highest-scoring next-token candidates.

It is a learning probe, not application code. It does not yet choose a
function, produce constrained JSON, validate a call with Pydantic, or run the
project's eventual function-calling workflow.

## Provenance: how we knew what to write

The probe was based on information already present in the repository:

- the public class and method signatures in `llm_sdk/llm_sdk/__init__.py`;
- the project rule that SDK private attributes must not be used;
- questions recorded in `docs/project/questions.md`;
- uncertainty about model construction, tensor shapes, decode behavior,
  tokenizer files, and returned logits;
- the need to learn through a repeatable experiment rather than assumptions.

Each SDK call corresponds to a specific question:

| SDK operation | Question being tested |
|---|---|
| `Small_LLM_Model(device=...)` | Can the supplied model wrapper construct successfully on this device path? |
| `encode(PROMPT)` | What tensor shape, dtype, device, and token IDs does the prompt produce? |
| `decode(encoded)` | What happens when the two-dimensional result of `encode()` is passed straight back? |
| `decode(encoded[0])` | What happens when only the first sequence is decoded? |
| tokenizer path getters | Which tokenizer artifacts exist, and where are they cached? |
| `get_logits_from_input_ids(input_ids)` | Can the SDK perform a forward pass, and how many next-token scores are returned? |
| `decode([token_id])` | What readable text corresponds to each high-scoring token ID? |

The assistant could plan these checks from the public interface, but it could
not know their runtime results in advance. For example, execution—not source
inspection—showed that a batched decode returns `list[str]` and that the CPU
probe returns 151,936 logits.

## How the experiment is invoked

There are two Make targets:

```bash
make inspect-sdk
make inspect-sdk-cpu
```

Their recipes are:

```make
inspect-sdk:
	uv run python experiments/inspect_sdk.py

inspect-sdk-cpu:
	uv run python experiments/inspect_sdk.py --device cpu
```

The command path is:

```text
make target
    -> runs the target's recipe
    -> uv selects or recreates the project environment
    -> Python executes experiments/inspect_sdk.py
    -> the module guard calls main()
    -> main() invokes the public SDK methods
    -> output and the process exit status show what happened
```

Running `make` is therefore not itself the experiment. Make selects and runs
the saved recipe; `uv run` supplies the project environment; Python runs the
actual experiment.

`make -n inspect-sdk-cpu` is different. The `-n` option is a dry run: it
prints the recipe but does not execute Python. It is useful for checking what
would run, but it cannot test the SDK.

## Environment and storage behavior

The Makefile exports these defaults:

```text
UV_PROJECT_ENVIRONMENT=/tmp/call-me-maybe-venv
UV_CACHE_DIR=/tmp/call-me-maybe-uv-cache
HF_HOME=/tmp/call-me-maybe-huggingface
UV_LINK_MODE=copy
```

Their roles are different:

- the project environment contains installed Python packages;
- the uv cache holds reusable downloaded or built package data;
- the Hugging Face cache holds the Qwen model and tokenizer files;
- copy mode avoids links back into the cache when installing packages.

Because these locations are under `/tmp`, the operating system may clear
them. That is acceptable: `uv` can rebuild the environment from
`pyproject.toml` and `uv.lock`, and Hugging Face can download the model again.
The successful CPU run demonstrated this after `/tmp` had been cleared.

## Source walkthrough

### Imports

`ArgumentParser` implements the optional `--device` command-line argument.
The allowed values are `cpu`, `cuda`, and `mps`.

`Callable` describes the type of the public path-getter functions passed to
`inspect_tokenizer_file()`.

`nlargest` selects the indices with the highest corresponding logit values.
It avoids sorting every score when only ten results are needed.

`Path` converts each returned path string into an object that can check
whether the file exists and query its size.

`perf_counter` measures elapsed construction and forward-pass time. It is
appropriate for durations; it is not being used as a calendar clock.

`Small_LLM_Model` is the supplied wrapper being investigated. The experiment
does not reach into its private fields.

### Constants

```python
PROMPT = "What is the sum of 2 and 3?"
TOP_CANDIDATE_COUNT = 10
```

The prompt is intentionally simple. At this stage the goal was to observe the
SDK mechanics, not to test function-calling quality. Ten candidates provide a
small readable sample of the logits vector.

### `parse_device_argument()`

This helper defines and parses `--device`. If the option is absent, it returns
`None`; that value is passed to the SDK's automatic device path. With
`--device cpu`, it returns `"cpu"` and changes only the constructor argument.

The parser is constructed with:

```python
ArgumentParser(description=__doc__)
```

`__doc__` is a special Python module attribute. Because this file begins with
a triple-quoted module docstring, Python stores that string in `__doc__` while
the module is loaded. Passing it as the parser description means
`python experiments/inspect_sdk.py --help` displays the same description. It
avoids maintaining a second copy of that explanatory text. If a module has no
docstring, its `__doc__` value is normally `None`, which `ArgumentParser` also
accepts.

The following `add_argument()` call defines one optional command-line input:

```python
parser.add_argument(
    "--device",
    choices=("cpu", "cuda", "mps"),
    help="Pass an explicit device to Small_LLM_Model.",
)
```

Those arguments were chosen for distinct reasons:

- `"--device"` gives the option its command-line spelling. The leading two
  hyphens make it optional, so the probe can still exercise automatic device
  selection when the option is omitted.
- `choices=("cpu", "cuda", "mps")` restricts input to the three device names
  accepted by the supplied SDK's public constructor: ordinary processor,
  NVIDIA CUDA GPU, or Apple's Metal backend. `argparse` rejects a typo or an
  unsupported value before model construction begins.
- `help=...` provides the short explanation shown beside the option in
  `--help` output.

No `type=` is required because command-line values are strings by default. No
`default=` is required because an omitted optional argument defaults to
`None`, which is precisely what the experiment needs to retain the SDK's
automatic-selection path. Finally, `.parse_args().device` returns the value
stored under the name inferred from `--device`.

The function docstring says it returns an “optional public SDK device
override.” “Optional” means the caller does not have to provide it. “Public
SDK” means the value is passed through the documented constructor parameter,
not written into a private field. “Override” means an explicit choice replaces
automatic device selection for that run. This is useful for predictable
hardware selection and, here, for isolating one variable after the automatic
path failed.

That single-variable change is important: it makes the default and CPU runs
useful as a controlled comparison.

### `print_heading(title)`

This helper only makes terminal output easier to scan. It has no effect on
model behavior.

### `inspect_tokenizer_file(label, path_getter)`

This helper accepts a label and one bound public SDK method. It:

1. calls the method to get a path string;
2. creates a `Path` object;
3. prints the path;
4. reports whether it is a file;
5. prints its size when present.

The local `try`/`except` lets the probe report one failed path method and then
continue checking the others. Catching `Exception` broadly would generally be
too permissive in production code, but here the purpose is to collect
diagnostic evidence from independent checks.

### `main()`

`main()` coordinates the experiment in five sections.

#### 1. Model construction

It parses the device, starts a timer, calls:

```python
model = Small_LLM_Model(device=requested_device)
```

and reports elapsed time. Construction errors are deliberately not caught.
If the model cannot load, Python prints the traceback and exits unsuccessfully
instead of allowing later output to imply that the full experiment succeeded.

The printed Qwen identifier documents the model expected from the supplied
wrapper. It does not itself select or configure the model.

#### 2. Encoding

```python
encoded = model.encode(PROMPT)
input_ids = encoded[0].tolist()
```

`encoded` is the SDK's tensor result. Indexing with `[0]` selects the first
sequence from the batch. Calling `.tolist()` converts that one-dimensional
tensor to the ordinary Python `list[int]` expected by
`get_logits_from_input_ids()`.

The program prints the prompt, tensor shape, dtype, device, token count, and
IDs so none of those properties need to be guessed.

#### 3. Decoding

The probe intentionally calls decode in two ways:

```python
model.decode(encoded)
model.decode(encoded[0])
```

Both calls are wrapped separately so that failure of the first form would not
prevent testing the second. The comparison investigates dimensionality:
`encoded` is a batch containing one sequence, while `encoded[0]` is the one
sequence itself.

#### 4. Tokenizer files

The three calls use the public getters:

- `get_path_to_vocab_file`;
- `get_path_to_merges_file`;
- `get_path_to_tokenizer_file`.

Passing these bound methods as values lets one helper perform the same
existence-and-size check for each without duplicating code.

#### 5. Next-token logits

```python
logits = model.get_logits_from_input_ids(input_ids)
```

This performs one model forward pass and returns a score for each possible
next token. These values are logits: raw comparative scores, not normalized
probabilities. A larger logit means the token is preferred relative to a
lower-scoring token in that position.

The selection code is:

```python
top_token_ids = nlargest(
    TOP_CANDIDATE_COUNT,
    range(len(logits)),
    key=logits.__getitem__,
)
```

`range(len(logits))` produces all possible indices. Here each index is also a
token ID. `key=logits.__getitem__` tells `nlargest` to compare those IDs using
the score stored at each index. The result is therefore the ten token IDs with
the highest scores, in descending order.

Each selected ID is passed as a one-item list to `decode()` so the terminal
can show both its numeric score and readable token text.

The logits call and candidate decodes are not caught. A failure makes the
experiment exit unsuccessfully, which is appropriate because they are central
to the result rather than optional metadata checks.

### Module guard

```python
if __name__ == "__main__":
    main()
```

When Python executes this file directly, `__name__` is `"__main__"`, so the
experiment runs. If another module imports the file, its functions and
constants become available without automatically loading the model.

## Data flow

```text
plain-text prompt
    -> model.encode(...)
    -> 2-D integer tensor: one batch x eleven tokens
    -> encoded[0]
    -> 1-D sequence tensor
    -> .tolist()
    -> list of integer token IDs
    -> model.get_logits_from_input_ids(...)
    -> 151,936 raw next-token scores
    -> select ten largest score indices
    -> decode each selected token ID
    -> readable candidate token fragments
```

Encoding and logits answer different questions. Encoding asks, “How is the
existing prompt represented?” Logits ask, “Given that prompt, how strongly
does the model score each possible next token?”

## The two real experiments

### Default device selection

Command:

```bash
make inspect-sdk
```

Observed result: model construction failed before encoding with a
`ValueError` stating that use of a `device_map` requires `accelerate`.

This failure proves that the particular automatic loading path reached during
that run needed `accelerate`. It does not prove that every platform or device
path needs it.

### Explicit CPU selection

Command:

```bash
make inspect-sdk-cpu
```

Observed result: the complete probe ran and exited successfully. Explicit CPU
was the only intended experimental change, supporting the hypothesis that the
earlier failure belonged to the automatic device-mapping path.

This does not repair or validate automatic/GPU selection. It establishes a
working CPU path for continued learning.

## Observed CPU results

### Construction

```text
model identifier: Qwen/Qwen3-0.6B
requested device: cpu
construction time: 18.419 seconds
```

### Encoding

```text
prompt: 'What is the sum of 2 and 3?'
tensor shape: (1, 11)
tensor dtype: torch.int64
tensor device: cpu
token count: 11
token IDs: [3838, 374, 279, 2629, 315, 220, 17, 323, 220, 18, 30]
```

The `1` is the batch size; `11` is the sequence length in model tokens. It is
not a count of words or characters. Integer token IDs use `torch.int64`.

### Decoding

```text
decode(encoded): ['What is the sum of 2 and 3?']
decode(encoded[0]): 'What is the sum of 2 and 3?'
```

The two-dimensional batch returned a list containing one string. The
one-dimensional sequence returned one string. This was an observed SDK
interface mismatch because the wrapper annotates `decode()` as returning
`str`, yet its own batched `encode()` output produces `list[str]` when decoded
directly.

Application code needing one string should pass one sequence, such as
`encoded[0]`, unless the supplied wrapper is deliberately repaired later.

### Tokenizer artifacts

| File | Exists | Observed size |
|---|---:|---:|
| `vocab.json` | yes | 2,776,833 bytes |
| `merges.txt` | yes | 1,671,853 bytes |
| `tokenizer.json` | yes | 11,422,654 bytes |

The paths were under the Qwen snapshot in
`/tmp/call-me-maybe-huggingface`. This confirms that all three public path
methods work with the cached Qwen3-0.6B tokenizer used in the experiment.

### Logits

```text
logit count: 151936
logits time: 0.301 seconds
```

There was one returned raw score for each token ID in the model vocabulary.
The ten highest-scoring decoded texts were:

```text
' What'
' To'
' Also'
' \n\n'
' How'
' And'
' Is'
' '
' The'
' Can'
```

These ordinary prose fragments do not indicate a broken model. The prompt
only asked a natural-language question. It did not tell the model:

- which functions are available;
- what those functions do;
- which arguments they accept;
- that it must choose a function;
- that output must follow a JSON schema;
- what prefix or chat template is required.

The run therefore tested next-token scoring, not semantic function selection.

## What the experiment proves—and what it does not

### Supported by execution

- the explicit CPU constructor path works in the tested environment;
- the prompt encodes to the recorded tensor and token IDs;
- direct batched decode and single-sequence decode have different return
  container types;
- all three tokenizer files exist through the public interface;
- one CPU forward pass returns 151,936 logits;
- the top candidates for the bare prompt are ordinary text fragments;
- deleting the `/tmp` environment is recoverable because `uv` recreated it.

### Not established

- that automatic device selection or CUDA now works;
- that adding `accelerate` is the correct long-term repair;
- that the model can yet choose the correct project function;
- that constrained decoding or JSON validation works;
- that the timings are stable benchmarks;
- that every prompt produces 11 tokens or every model has this vocabulary;
- that the experiment is production-ready application architecture.

## Common questions and concise answers

### Did we create this file or download it?

We created it locally with AI assistance. Its docstring, experiment README,
and Waypoint 007 record that provenance.

### Was it generated automatically?

No tool generated it as a project artifact. The assistant authored the code
from a human-readable experiment plan based on the SDK's public methods. The
runtime values were then obtained by executing that code.

### How did the assistant know what to put in it?

By mapping each unresolved question to the smallest public method call that
could produce evidence, then adding standard-library code to time, display,
and compare the results.

### What is `__doc__`?

It is the special attribute through which Python exposes the docstring of the
current module, class, or function. At module level in this file, `__doc__`
contains the explanatory string at the very top of `inspect_sdk.py`. The
script passes it to `ArgumentParser` so that text appears in `--help` output.

### What does “optional public SDK device override” mean?

The command may omit `--device`, in which case the SDK selects automatically,
or provide one documented device value to replace that automatic choice for
the run. The explicit CPU override gave us a controlled way to test whether
the earlier failure belonged to automatic device mapping.

### What are device arguments, and why are they useful?

They are command-line values selecting the computation backend: CPU, an
NVIDIA GPU through CUDA, or Apple's GPU through MPS. They let the same probe
choose hardware without editing its source and let experiments compare device
paths explicitly.

### Why does `--device` use these parser arguments?

The option name mirrors the SDK constructor's `device` parameter; `choices`
limits input to the constructor's CPU, CUDA, and MPS values; and `help`
explains the option in the generated help screen. Omitting a default
intentionally produces `None`, preserving automatic selection when the option
is not used.

### What exactly does Make do here?

It finds the named target and executes its stored shell recipe. The recipe
runs Python through `uv`; Python, not Make, performs the SDK calls.

### How do we know it genuinely ran?

The real run produced model-loading activity, elapsed timings, tensor data,
decoded return values, file sizes, 151,936 model scores, candidate texts, and
exit code `0`. A dry run could produce none of those runtime facts.

### Why use explicit CPU?

It changed one constructor value after the automatic path failed. The result
isolated a working path without immediately changing dependencies, making the
experiment easier to interpret.

### Why not just install `accelerate`?

Installing it might make the automatic device-map path proceed, but that
would change a second variable before learning whether the public CPU option
already worked. The CPU test answered that narrower question first. GPU and
automatic-device requirements remain a separate decision.

### Are logits probabilities?

No. They are raw model scores. A softmax operation can transform a vector of
logits into probabilities, but this probe does not need probabilities to rank
the candidates because softmax preserves their order.

### Why does `nlargest` receive indices rather than logits directly?

The program needs token IDs after ranking. Ranking the indices with their
associated scores preserves each score's position, and that position is the
token ID used by `decode()`.

### Why decode both `encoded` and `encoded[0]`?

To test whether the wrapper handles a batch and a single sequence in the same
way. The differing container types exposed a useful interface inconsistency.

### Why are some failures caught while construction is not?

Decode forms and file getters are independent diagnostic checks, so the probe
can report one failure and continue gathering evidence. Construction and
logits are central milestones; if either fails, a nonzero exit and traceback
make the incomplete run unmistakable.

### Why did the top candidates not answer `5`?

The printed candidates are the model's very next token after a bare question,
not a complete generated answer. The wrapper also did not apply a chat
template or instruction to answer directly. A full answer would require a
generation loop that repeatedly chooses and appends tokens.

### Does the probe modify project data?

It does not modify source or input data. It may create or refill the external
Python and Hugging Face caches required to run the model.

## Likely misconceptions to correct

- `make -n` is not evidence that the Python program ran.
- A successful CPU run does not mean the automatic-device failure is fixed.
- `(1, 11)` means one sequence of eleven tokens, not eleven independent
  prompts.
- Token IDs are vocabulary references, not Unicode character codes.
- The logit count is vocabulary size, not prompt length.
- One logit vector represents one next-token decision, not a generated reply.
- The top candidate is not automatically the candidate that must be chosen;
  later decoding policy may sample or apply constraints.
- A model cannot select among project functions that have never been
  described in its input.
- A 0.301-second forward pass is not a full end-to-end application benchmark.
- Diagnostic exception handling should not automatically be copied into
  production code.

## Good follow-up discussion questions

1. Which statements in this document come from source inspection, and which
   required a real run?
2. Why is the CPU comparison stronger evidence than changing the dependency
   list and device behavior simultaneously?
3. How do batch dimension and sequence dimension explain the two decode
   return values?
4. Why can token IDs double as indices into the logits vector?
5. What additional context must a function-calling prompt contain?
6. What would a generation loop need to do after receiving the first logits
   vector?
7. At what stage should constrained decoding limit allowed next tokens?
8. Where should Pydantic validation occur, and what would it validate?
9. Which parts of this probe are reusable diagnostics, and which are specific
   to this one learning question?
10. What evidence would be needed before deciding to add `accelerate`?

## Guidance for the discussing agent

- Lead with an explanation, then ask the learner to restate it in their own
  words.
- Use the actual values above when explaining tensors, decode types, and
  logits.
- Label source facts, observed facts, hypotheses, and open decisions.
- Do not present the probe as production code or as completed function

- Do not imply that automatic/GPU loading was repaired.
- If proposing a next experiment, explain its question, controlled variable,

## Recommended next conceptual step

Before implementing constrained generation, design the smallest prompt that
teaches the model the available function names, descriptions, parameter
schemas, and required output shape. Then run another controlled probe to see
whether the model's next-token scores begin to reflect that information.

That future experiment should remain separate from `inspect_sdk.py` so this
file continues to document the basic public SDK behavior already observed.

## Quick glossary

| Term | Meaning here |
|---|---|
| token | A model vocabulary unit; it may be a word, fragment, space, punctuation, or another text piece |
| token ID | The integer position identifying a token in the vocabulary |
| tensor | PyTorch's multidimensional numeric data container |
| batch | A group of sequences processed together; this probe has a batch size of one |
| sequence length | Number of token IDs in one encoded input |
| decode | Convert token IDs back into text |
| logit | A raw score for a possible next token |
| forward pass | Run input through the model once to obtain output scores |
| vocabulary size | Number of token IDs the model can score; observed here as 151,936 |
| device | Hardware/backend used for tensor computation, such as CPU or CUDA |
| cache | Re-downloadable local data used to avoid repeated package or model downloads |
| controlled experiment | A comparison intended to change one relevant variable at a time |
