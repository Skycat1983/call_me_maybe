## Essential summary

`inspect_sdk.py` is a small diagnostic program written locally with help from
the AI assistant. It was not supplied with the project, downloaded, generated
by `uv`, or generated by the Qwen model.

It was designed by reading the supplied SDK's public interface and turning
the project's open questions into observable checks. The program:

1. constructs `Small_LLM_Model`;
2. encodes one prompt into token IDs;
3. tests two forms of decoding;
4. asks the SDK for its three tokenizer-file paths;
5. requests one vector of next-token logits;
6. finds and decodes the ten highest-scoring next-token candidates.

It is a learning probe, not application code. It does not yet choose a
function, produce constrained JSON, validate a call with Pydantic, or run the
project's eventual function-calling workflow.

## Provenance: how we knew what to write

The probe was based on information already present in the repository:

- the public class and method signatures in `llm_sdk/llm_sdk/__init__.py`;
- the project rule that SDK private attributes must not be used;
- questions recorded in `docs/project/questions.md`;
- uncertainty about model construction, tensor shapes, decode behavior,
  tokenizer files, and returned logits;
- the need to learn through a repeatable experiment rather than assumptions.

Each SDK call corresponds to a specific question:

| SDK operation | Question being tested |
|---|---|
| `Small_LLM_Model(device=...)` | Can the supplied model wrapper construct successfully on this device path? |
| `encode(PROMPT)` | What tensor shape, dtype, device, and token IDs does the prompt produce? |
| `decode(encoded)` | What happens when the two-dimensional result of `encode()` is passed straight back? |
| `decode(encoded[0])` | What happens when only the first sequence is decoded? |
| tokenizer path getters | Which tokenizer artifacts exist, and where are they cached? |
| `get_logits_from_input_ids(input_ids)` | Can the SDK perform a forward pass, and how many next-token scores are returned? |
| `decode([token_id])` | What readable text corresponds to each high-scoring token ID? |

The assistant could plan these checks from the public interface, but it could
not know their runtime results in advance. For example, execution—not source
inspection—showed that a batched decode returns `list[str]` and that the CPU
probe returns 151,936 logits.

## How the experiment is invoked

There are two Make targets:

```bash
make inspect-sdk
make inspect-sdk-cpu
```

Their recipes are:

```make
inspect-sdk:
	uv run python experiments/inspect_sdk.py

inspect-sdk-cpu:
	uv run python experiments/inspect_sdk.py --device cpu
```

The command path is:

```text
make target
    -> runs the target's recipe
    -> uv selects or recreates the project environment
    -> Python executes experiments/inspect_sdk.py
    -> the module guard calls main()
    -> main() invokes the public SDK methods
    -> output and the process exit status show what happened
```

Running `make` is therefore not itself the experiment. Make selects and runs
the saved recipe; `uv run` supplies the project environment; Python runs the
actual experiment.

`make -n inspect-sdk-cpu` is different. The `-n` option is a dry run: it
prints the recipe but does not execute Python. It is useful for checking what
would run, but it cannot test the SDK.

## Environment and storage behavior

The Makefile exports these defaults:

```text
UV_PROJECT_ENVIRONMENT=/tmp/call-me-maybe-venv
UV_CACHE_DIR=/tmp/call-me-maybe-uv-cache
HF_HOME=/tmp/call-me-maybe-huggingface
UV_LINK_MODE=copy
```

Their roles are different:

- the project environment contains installed Python packages;
- the uv cache holds reusable downloaded or built package data;
- the Hugging Face cache holds the Qwen model and tokenizer files;
- copy mode avoids links back into the cache when installing packages.

Because these locations are under `/tmp`, the operating system may clear
them. That is acceptable: `uv` can rebuild the environment from
`pyproject.toml` and `uv.lock`, and Hugging Face can download the model again.
The successful CPU run demonstrated this after `/tmp` had been cleared.
